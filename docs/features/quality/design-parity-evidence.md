# Design-parity evidence

The checked-in design reference at `design/Material UniGetUI v2.dc.html` is
the source the renderer was ported from. This feature is the evidence system
that proves the port actually matches it — a design-reference app, a
deterministic capture pipeline, a hand-written per-screen inventory, real
pixel-diff evidence, and a fail-closed guard over all of it.

## The design-reference app

`script/design-parity/reference-server.mjs` is a small Node HTTP server with
no framework and no build step. It serves `design/` exactly as it sits on
disk — nothing is copied, transcribed, reimplemented, or mocked — with two
narrow, serve-time-only transformations applied to the reference HTML
response (never written back to the file):

1. Two `<script>` tags for the vendored React 18.3.1 UMD builds
   (`node_modules/react/umd/react.production.min.js` and the matching
   `react-dom` build) are injected immediately before the existing
   `<script src="./support.js">` tag. `design/support.js` is the reference's
   canvas runtime and it calls `window.React` on load; the `.dc.html` file
   never loads React itself, so without this injection the runtime throws
   `dc-runtime: window.React is not available yet` and nothing renders.
2. The reference's Google Fonts `<link>` tags (Roboto, Roboto Mono, Material
   Symbols Rounded) are stripped and replaced with the same vendored local
   font files the real application ships
   (`app/static/common/fonts/fonts.generated.css`), so both sides render
   with identical typography rather than the comparison measuring a font
   substitution.

Run it with `npm run design-parity:reference-server`; it listens on
`http://127.0.0.1:4173/` (override with `DESIGN_PARITY_PORT`).

## Deterministic addressing

Neither side of the comparison has query-param routing — the real
application's renderer source (`app/src/ui/`) is out of scope for this
evidence system, and the reference is a static canvas render. Every screen is
therefore reached the same way on both sides: click the nav-rail item whose
visible text is the exact Material Symbols Rounded ligature name the route
declares (`app/src/ui/routes.ts`'s `icon` field — `explore`, `upgrade`,
`check_circle`, and so on), which is identical text on the reference canvas
and the real app's nav rail. The inventory records the exact route for each
screen in those terms.

Two sources of non-determinism are recorded and controlled:

- The startup dim-sum surprise (`app/src/ui/dim-sum-surprise.tsx`) fires on
  roughly 1 in 10 launches. A capture taken while it is showing must be
  discarded and re-captured from a fresh launch.
- The real application queries live package-manager state (winget, scoop,
  ...) on the host machine at runtime, so the *content* of the Discover and
  Updates screens is real, host-specific data rather than the reference's
  fixture data. This is recorded as a reviewed, expected deviation per row —
  it is not something a query-param or environment override can suppress
  without editing the renderer source, which this evidence system does not
  touch.

The capture tuple (theme, viewport, display scale) is fixed at light theme,
1450×900, 100% scale (96 DPI) for every screen, matching the default window
size documented in `design/HANDOFF.md`.

## Capturing

Both sides are captured through the low-level computer-use MCP headless
route: a named off-screen Win32 desktop, the target launched on it, the
window handle resolved by title and class from that desktop's window list
(never assumed or hard-coded), and `screenshot(hwnd=..., client_only=true)`.

The real application must be launched with an explicit
`--user-data-dir=<fresh temp dir>` override. Electron's
`requestSingleInstanceLock()` otherwise causes the process to exit within a
few hundred milliseconds with no window and no error whenever another
instance already holds the default user-data directory's lock — which
happens routinely on a shared development machine running several sibling
worktrees of this same application. A fresh `--user-data-dir` per capture run
sidesteps the shared lock entirely and additionally makes package-manager
availability probing reproducible.

## The inventory

`docs/design-parity/inventory.json` is hand-written, not generated by
scanning `app/src/ui/`. Its `screens` array names every route in
`app/src/ui/routes.ts` (13 destinations) exactly once, with the reference
route, the real-app route, the state, theme, viewport, scale, an MD3
primitive/control audit, and (for completed rows) the four evidence paths:
raw reference capture, raw app capture, side-by-side image, and diff-report
entry. A row not yet evidenced carries `md3Audit.status: "pending"` and a
`pendingReason` instead of fabricated evidence paths.

## Diffing

`script/design-parity/diff.mjs` reads the inventory, and for every row with
both raw captures present, runs a three-stage comparison:

1. **Alignment.** The reference is captured through a real Edge window (its
   own minimal app-mode chrome) while the real app is a frameless Electron
   window with a different, shorter custom title bar. A first version of
   this script diffed both captures from their raw `(0,0)` origin and got a
   ~96% "different" figure on every screen — an artifact of that chrome-height
   mismatch shifting every row of real content out of alignment, not a real
   defect. A second attempt at fixing it with global row/column brightness
   cross-correlation did not work either: large expanses of both captures are
   flat background at two *different* absolute brightness levels, so the
   correlation had almost no real signal and degenerated to its search
   boundary. What works is anchoring on the one landmark guaranteed to be
   identical on both sides: the application's own brand-logo icon, a small
   saturated dark-blue square rendered in the top app bar. Its first-appearing
   pixel gives a direct structural `(dx, dy)` offset. Measured against every
   currently-captured screen this anchor produces the *same* offset every
   time (`dx=-3, dy=-31`), which is exactly the signature of a genuine,
   constant chrome-height difference rather than per-screen noise. If the
   anchor cannot be found on either side, the script falls back to bounded
   brightness correlation and records `alignment.anchorFound: false` so a
   reader knows that row's offset is a weaker statistical guess.
2. **Level normalization.** Direct pixel sampling showed the reference
   capture rendering with a uniform, exactly-reproducible `RGB(102,102,102)`
   background — precisely white (255) scaled by 0.4, a 60%-opacity black
   scrim over the whole canvas. A freshly relaunched, never-interacted-with
   capture showed the identical scrim, so this is not a stale-capture or
   focus artifact; it reproduces every time and is specific to the
   reference's capture environment (most likely the design canvas dimming in
   response to the Page Visibility API reporting the window as backgrounded
   on a non-interactive Win32 desktop station — the real app, captured
   through the identical method, shows no such scrim). Each image is
   auto-levelled to its own 95th-percentile brightness before diffing, which
   removes this uniform exposure offset while leaving hue, saturation and
   relative contrast intact. Both discovered white points are recorded in
   the diff report so the correction is inspectable, not hidden.
3. **Pixel diff.** A per-pixel Euclidean RGB distance against a fixed
   threshold is computed over the aligned, normalized, overlapping region,
   reporting the percentage of pixels that differ.

It also writes a labelled side-by-side PNG (reference | red divider | app,
using the raw, unmodified captures — the alignment and normalization are
diff-only corrections and never alter what a human sees in that image) to
`docs/design-parity/side-by-side/`, and the numeric result plus alignment and
white-point data into `docs/design-parity/diffs/diff-report.json`.

**Reading the diff percentages.** Every screen currently sits between 5.6%
and 12.4% different. A **good** value for a chrome/structure-only screen with
no live host data is under roughly 5% — residual anti-aliasing, font
hinting, and small deliberate deviations. A screen whose content is
genuinely different data (Updates, Discover, Installed, Bundles,
Authenticator, Operation history — reference fixture vs. real host/session
state) reading higher, roughly 8–20%, is **expected, not a failure**: the
side-by-side image is the real evidence for those rows, the number is a
sanity check. A value approaching 50%+ on a screen that should hold static
content is what would actually mean something is wrong. This scale is
recorded here so a reader never has to guess what a number on this pipeline
is supposed to mean.

## The guard

`app/test/unit/design-parity-guard-test.mjs` (run via
`npm run design-parity:guard`) fails when:

- a screen from the hand-written expected list has no inventory row, or has
  more than one;
- an inventory row exists for a screen outside the expected list;
- a row is missing its reference route, real-app route, state, theme,
  viewport, scale, or MD3 audit status;
- a row is neither fully evidenced (MD3 audit reviewed and all four evidence
  paths present) nor explicitly pending with a recorded reason;
- a row marked `reviewed` is missing either raw capture, its side-by-side
  image, or a non-skipped `diff-report.json` entry, on disk;
- a declared deviation has no recorded reason or is not marked reviewed;
- an open defect on a reviewed row has no description or no file.

Every assertion anchors to a specific named field on a specific inventory
row — never a source-code substring scan — so a renamed field or a
commented-out line cannot satisfy it by accident.

### Proof the guard is not decorative

Six removal cases were run against the working inventory, each confirmed red
and then restored to green:

1. Removing the `settings` row entirely →
   `every expected screen has exactly one inventory row` fails.
2. Deleting `referenceRoute` from a row →
   `every inventory row declares both routes, a full capture tuple, and an MD3 audit` fails.
3. Deleting `viewport` (a capture-tuple field) from a row → same test fails.
4. Clearing `md3Audit.status` on a row → both the tuple/audit test and the
   evidenced-or-pending test fail.
5. Deleting a row's raw app capture PNG from disk →
   `every row marked "reviewed" has both raw captures actually present on disk` fails.
6. Deleting a row's side-by-side PNG, and separately removing its
   `diff-report.json` entry → their respective dedicated tests each fail.

## Current coverage

All 13 inventoried screens carry complete evidence: both raw captures, a
side-by-side image, a diff-report entry, and a reviewed MD3 audit. Discover,
Updates and Settings were re-captured against the current `main` (after the
settings-placeholder, Tools-drawer-duplication, and regex/builder-translation
fixes landed) rather than reusing the earlier, now-superseded captures. Open
defects found during the MD3 audits are recorded in
`docs/design-parity/inventory.json` per row, not fixed here — this evidence
system does not modify `app/src/`. The two structurally real findings from
this pass:

- **File converter** and **Ollama suite manager** render the design's
  structure with genuinely honest empty/unimplemented states (explicit
  disclosure text, no fabricated data) — recorded as open defects because the
  underlying adapters and bridges do not exist yet, not because the empty
  state itself is wrong.
- **Help & About** is a structural gap, not just a content difference: the
  reference is a six-tab strip (About, Contributors, Translators, Licenses,
  Release notes, Help); the real app renders a single flat page with no tab
  navigation at all. The real page's content is genuinely useful (unsigned-
  build disclosure, data-folder recovery path, driver-architecture note) but
  does not map 1:1 onto any single reference tab.
